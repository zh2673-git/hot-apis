# 反模式库

> 依据 `project-development-prompt.md` §六「反模式库自进化」：每轮失败时提取新模式。
> 每条包含：现象 → 根因 → 检出方式 → 纠正 → 适用面。

---

## AP-1 验证工具自身覆盖基线（自证式验证）

**现象**：`capture_baseline.py --compare` 连续两次跑都"全部等价"，包括明显已失效的平台。

**根因**：采集函数不分模式都写盘，`--compare` 先把基线文件覆盖成"改造后"的数据，
再拿它跟"改造后"比 —— 比对**必然通过**。

**检出方式**：跑完比对后执行 `git status --short docs/baseline/`，若基线文件被改动
即说明比对不可信。**这是最容易自我欺骗的一类缺陷**：测试通过得越顺利越可疑。

**纠正**：写盘必须由显式开关控制（`persist=args.record and not args.compare`）；
比对只读、绝不写。

**适用面**：所有"基线/快照/黄金样本"型回归测试（golden test、snapshot test、approval test）。

## AP-2 断言比"分片边界"而非"聚合结果"

**现象**：流式解析单测 A-P1 在某个切点失败：
`['好','的','完成'] != ['好的','完成']`，但拼接后完全相同。

**根因**：把 SSE 分片边界当成了契约的一部分。实际上客户端只对**聚合结果**负责，
分片位置由缓冲策略与网络时序决定，不构成对外契约。

**检出方式**：断言里出现"逐元素比较分片列表"而非"先 join 再比"。

**纠正**：流式相关的断言一律先聚合再比较；若确实要约束分片，需在方案里显式声明
（例如"首帧必须携带角色"这类真实契约）。

**适用面**：所有流式/分块处理的测试（SSE、WebSocket 帧、分页、chunked transfer）。

## AP-3 用例题目歧义（测到了模型常识，没测到被测能力）

**现象**：U2「多工具需选择」在 deepseek 返回
`"请告诉我你要查询的城市名称"`，在 kimi 返回 `"当前时间是 2026年9月11日 06:19"`。

**根因**：题目本身有歧义 ——
① 工具参数 `city` 是必填，但题目没给城市 → 模型**合理地**反问；
② 该信息模型可自行作答 → 按 U3 的定义（可自答就不该调工具）它**就该**不调工具。
两个失败都不是能力问题，而是**用例设计问题**，却被当成了能力指标。

**检出方式**：失败详情里出现"反问""直接给出答案"这类**在语义上正确的替代行为**。

**纠正**：用例必须满足两条硬条件 ——
**信息不可自答**（否则直接回答是正确行为）+ **参数齐备**（否则反问是正确行为）。
修正后 U2 改为「帮我查一下上海现在的天气」，4 个平台中 3 个立即通过。

**适用面**：所有 LLM 行为评测。判断标准是"这个失败是否可能是正确行为"。

## AP-4 把上游空响应当作结构回归

**现象**：I1 比对中 doubao / zhipu 判为"❌ 不等价"，差异是流式首帧结构不同：
baseline 是内容帧，current 是终止帧（`delta:{}, finish_reason:"stop"`）。

**根因**：断言拿 `frames[0]` 直接比。上游本次**没产出内容**时，帧序列自然不同 ——
这是上游波动，不是本项目的结构回归。

**检出方式**：差异表现为"帧数量变化/首帧变成终止帧"，而非"同一帧的字段增删"。

**纠正**：按**帧形状**分类比对（内容帧形状 / 终止帧形状），并显式统计
`has_content`；上游空响应记为 **SKIP 并打印说明**，不计入失败。
关键是**显式标注**，不能静默忽略。

**适用面**：任何依赖外部服务输出的回归比对。

## AP-5 固定长度尾窗（把"安全"做成了"延迟"）

**现象**：单测 A-P4 失败 —— 纯文本 `"你好"` 一个字符都没吐出来。

**根因**：为跨 chunk 检测定界符，实现里扣留固定 10 字符尾窗。于是任何短于 10 字符的
纯文本都被整体扣住，直到更多内容到达或生成结束。方案里承诺的"快路径零延迟"落空。

**检出方式**：断言"首 chunk 必须立即产出"——**只要有固定缓冲，这条断言必然失败**。

**纠正**：扣留长度改为**动态计算**：只保留"最长的、且是某个定界符前缀的后缀"
（`_safe_tail_length`）。纯文本后缀不可能是定界符前缀 → 保留 0 → 立即产出。

**适用面**：所有流式增量解析（markdown 流式渲染、代码块嗅探、标签协议）。

## AP-6 把输出格式规则只写在 prompt 开头

**现象**：L 维度首轮仅 75%/75%/50%，U5（工具结果回传后继续）在多平台失败，
模型重复调用工具而不基于结果作答。

**根因**：工具规范与调用规则全部位于 prompt **前部**，而模型对 prompt 末端的
注意力权重最高；同时缺少"已有工具结果就不要重复调用"这条约束。

**检出方式**：失败模式是"格式不遵守"而非"能力不足"（模型知道该做什么，但没照做）。

**纠正**：① 在 prompt **最末端**追加 `[输出要求]` 强提醒；
② 增加规则 5「若 `<conversation>` 中已存在该工具的 `<tool_result>`，必须直接依据结果作答」。
修正后 deepseek/kimi/doubao 全部达到 100%。

**适用面**：所有提示词工程；尤其是"必须严格遵守格式"的约束。

## 汇总

| 编号 | 类型 | 一句话记忆 |
|---|---|---|
| AP-1 | 验证方法 | 验证工具不得修改基线，否则自证正确 |
| AP-2 | 断言设计 | 比聚合结果，不比分片边界 |
| AP-3 | 用例设计 | 失败的"正确替代行为"不是能力缺陷 |
| AP-4 | 断言设计 | 上游波动要 SKIP 并标注，不要判为回归 |
| AP-5 | 实现设计 | 固定缓冲 = 固定延迟；按需扣留才是快路径 |
| AP-6 | 提示词设计 | 规则要出现在末端，并覆盖"重复调用"这类反直觉分支 |
