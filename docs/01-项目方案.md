# NXAPI 工具调用适配层 · 项目方案

> 依据 `program.md`（模式：**生产**）与 `project-development-prompt.md`「时空运行时模型」产出。
> 生成时间：2026-09-11 ｜ 目标语言：Python 3.11 ｜ 目标形态：OpenAI 兼容工具调用端点

---

## 项目目标

让 `hot-apis`（NXAPI）的 `/v1/chat/completions` 支持 **OpenAI 标准工具调用**，
使 Cline / Roo Code / Continue / OpenCode 等 agent 能把它直接当作模型后端。

四条可验收口径：

1. **协议可识别**：客户端发送 `tools` + `messages`（含 `role:"tool"`），服务端返回符合
   OpenAI 规范的 `tool_calls`（流式与非流式皆可）。
2. **多轮可闭环**：把工具执行结果以 `role:"tool"` 回传后，模型能基于结果继续作答。
3. **零回归**：不传 `tools` 时，响应与改造前**逐字段等价**（I1）。
4. **可量化**：固定用例集上的工具调用成功率 **≥ 80%**（L 维度）。

**根因说明**：本项目上游是 Web 逆向得到的聊天接口（`chat.deepseek.com`、`www.kimi.com`、
`www.doubao.com` …），它们**只收自然语言、只回自然语言，没有 `tools` 参数**。
所以工具能力不可能"透传"获得，**只能在 relay 内部用提示词注入 + 输出解析合成**。

## 本质定义（必须通过时空契约校验）

**本质**：一个**无状态的协议翻译层** —— 把「只能收自然语言、只能回自然语言」的聊天模型，
包装成「能收 JSON Schema 工具规范、能回结构化 `tool_calls`」的 OpenAI 兼容端点。

它不是模型服务，不是 agent 框架，**只是一层双向翻译**：
`tools 规范 → 自然语言提示`（正向）与 `自然语言输出 → tool_calls 结构`（逆向）。

### 时空契约校验

- **空间归属（谁独占/何时回收）**
  - `tools` 定义、渲染出的提示文本、解析缓冲：**请求独占**，请求返回即随对象释放（Python 作用域回收）。
  - 工具调用的**多轮状态不驻留 relay**：agent 每轮自带完整历史，relay 无状态。
    既有的 `provider._sessions`（上游会话 id）仅作**连接复用优化**，不承载正确性。
  - 跨请求唯一驻留空间是 `src/api.py` 的模块级 `providers` 字典，回收由既有 `lifespan` 的
    shutdown 调 `provider.close()` 完成。

- **时间流形态（顺序 / 循环 / 状态机）**
  - 主流程：**顺序管道** `HTTP → 取 provider → 上游 → 解析 → SSE`，不引入并发。
  - 新增一处**状态机跳转**：解析器在流式文本上跨 chunk 维持
    `NORMAL → IN_TOOL_CALL → NORMAL`，在 `IN_TOOL_CALL` 内累积 JSON 至定界符闭合才提交。

- **规则拦截（编译时 / 运行时）**
  - 全部为**运行时**拦截：pydantic 结构校验（R4）+ 解析层降级（R2）。
    Python 无编译期约束可用，故不变量只能靠**断言式测试**（I1–I5）守。

### 类归属

属于「**API 网关的语义增强层 / 协议适配器**」。

- 不是「模型服务」：它不产 token，只翻译。
- 不是「agent 框架」：它不持有"思考—行动"循环，循环属于客户端；本层把循环**折叠进一次 API 调用**。

### 关键属性展开

| # | 本质属性 | 代码落点 |
|---|---|---|
| A1 | **双向翻译**：规范↔自然语言两个方向的映射 | `src/tools/render.py`（正向）、`src/tools/parse.py`（逆向） |
| A2 | **无状态**：正确性不依赖任何跨请求缓存 | 全部状态在请求作用域内；`pipeline.prepare/finalize` 为纯函数 |
| A3 | **自包含**：每轮必须自带完整历史（上游会丢上下文） | `render.render_messages()` 把历史**压平成单条文本** |
| A4 | **容错降级**：解析失败不得影响可用性 | `parse` 返回 `(content, tool_calls)`，失败即 `tool_calls=[]` |
| A5 | **零侵入**：不传 `tools` 时路径完全不变 | `api.py` 前置分支 `if not request.tools: 原逻辑` |
| A6 | **可观测**：工具调用成功率可被量化 | `verify_tools.py` 固定用例集 + L 维度统计 |

**只有本层必须自己制造工具语义**——这是全部设计取舍的来源。

### 第0级时空映射表

| 时空层级 | 本项目对应 | 物理目录 | 核心职责（时空视角） |
|---|---|---|---|
| 数据规范（规则基座） | 请求/响应模型、工具规范、定界符与提示模板 | `src/models/schemas.py`、`src/tools/spec.py` | 定义内存布局与类型规则；零依赖 |
| 数据存储（空间落地） | **无持久化** | — | 显式声明无存储，杜绝空间泄漏面 |
| 流转-核心规则（业务时空） | 渲染与解析纯函数 | `src/tools/render.py`、`src/tools/parse.py` | 双向翻译规则；不依赖 provider 具体实现 |
| 流转-编排（调度时空） | 一次工具调用轮的组装 | `src/tools/pipeline.py` | 串联 render → 上游 → parse，管理请求级状态 |
| 运行时/内核（时空管家） | FastAPI 应用与 `lifespan` | `src/api.py` | 既有：启动即建 provider 缓存、关闭时 `close()`。**工具层无状态，故无新增钩子** |
| 数据接口（时空入口） | `/v1/chat/completions`、`/v1/models` | `src/api.py` | OpenAI 兼容入口；`/v1/models` 本次不改 |

### 依赖方向铁律校验（时空防越界）

- ✅ **空间防越界**：`src/tools/*` 只依赖 `src/models/schemas.py`，**不 import 任何 provider**；
  provider 由 `pipeline` 以参数形式接收（依赖注入），符合"领域层不直接依赖基础设施"。
- ✅ **时间防乱序**：`tools` 层不触碰调度器/生命周期，只做纯计算；上游调用由 `pipeline` 发起。
- ✅ **规则防穿透**：跨层数据一律经 `schemas.py` 定义的类型流转，禁止裸 dict 穿透到 provider。

### 技术选型理由（由本质 + 时空需求推导）

| 选型 | 理由（因果链） |
|---|---|
| **沿用 Python 3.11 + FastAPI，不引入新依赖** | 本质是"翻译层"，无算力/并发需求；上游延迟与协议变更才是风险源。新依赖只增加攻击面与部署成本，不解决根因 → I4 与 R5 |
| **提示词模拟（方案 A），不做本地模型解析** | 上游零工具能力是**硬约束**，本地无法凭空获得工具语义；翻译层是唯一不更换上游的路径 |
| **多格式容错解析（标签 / 围栏 / 裸 JSON）** | 时空需求"规则拦截只能在运行时"→ 必须假设模型输出**不可信**，用多候选格式提高成功率 |
| **流式状态机而非整包解析** | 上游多数只支持流式（MiniMax 非流式实测 30–40s）→ 必须流式；而流式意味着 JSON 会被 chunk 切开 → 必须状态机 |
| **历史压平成单条文本** | 上游 `kimi`/`doubao`/`qwen` 只取最后一条 user 消息（见 §约束）→ 若不做压平，agent 的历史与工具结果会被整体丢弃 |
| **不引入 Anthropic `/v1/messages`** | 范围锁定 OpenAI 兼容客户端；Anthropic 端点属独立迭代，避免方案膨胀 |

## 模块递归四层设计（强制带生命周期钩子）

### 模块 `tools`（第1层）

- **本质（锚定父本质 + 时空契约）**：
  在"无状态协议翻译层"（父本质）的时空约束下，本模块的本质是
  **一个纯函数集合，负责 `tools+历史 → 文本` 与 `文本 → tool_calls` 的双向映射，全程无副作用**。
  空间上不持有任何跨请求状态；时间上除 `parse` 内部的局部状态机外无控制流跳转；规则上以"降级"为唯一失败策略。

- **数据规范**：`ToolSpec` / `FunctionSpec` / `ToolCall` 数据结构；工具调用定界符常量；提示词模板常量。
  落点：`src/tools/spec.py` + `src/models/schemas.py` 新增字段。
- **数据存储**：**无**。显式声明：本模块不写文件、不连库、不缓存 → 无空间泄漏面。
- **数据流转**：
  - `render.build_system_prompt(tools, tool_choice) -> str`：规范 → 约束文本
  - `render.render_messages(messages, tools, tool_choice) -> List[ChatMessage]`：历史压平为单条 user 文本
  - `parse.ToolCallStreamParser.feed(chunk) -> List[Event]`：流式状态机
  - `parse.extract(text) -> (content, tool_calls)`：整包解析（非流式 / 收尾用）
- **数据接口**：`pipeline.prepare(request) -> PreparedRequest`、`pipeline.finalize(text) -> Response`、
  `pipeline.stream(...) -> AsyncGenerator`。三者是 api 层唯一触点。
- **生命周期钩子实现**：
  | 钩子 | 是否适用 | 说明 |
  |---|---|---|
  | `init(ctx)` | ❌ 不适用 | 无需开辟空间：无缓存、无连接池、无全局表。**显式声明"无 init"是本设计的关键**——任何"为了对称而写的 init"都会引入跨请求状态，违反 3.1 |
  | `start()` | ❌ 不适用 | 无独立执行流；调用由 HTTP 请求驱动（宿主运行时即 `api.py` 的 ASGI 事件循环） |
  | `stop()` | ❌ 不适用 | 无持续运行的时间流可暂停 |
  | `destroy()` | ❌ 不适用 | 请求级对象随请求作用域回收（CPython 引用计数）。唯一需要显式回收的资源是**上游 httpx client**，它属于既有 `providers`，由既有 `api.lifespan` 关闭（**本次不改**） |

  > 与 §2.3「强制带生命周期钩子」的对应说明：本模块**显式声明四个钩子均不适用并给出理由**，
  > 等价于"按依赖逆序回收"的结论——因为依赖为空，回收顺序为空。

- **子模块（第2层）**

  **`render`（第2层）**
  - 本质：在"双向映射纯函数集合"约束下，本子模块是**正向映射器**（结构 → 自然语言）。
  - 四层：规范=提示模板常量；存储=无；流转=字符串拼装（顺序管道）；接口=`build_system_prompt` / `render_messages`。
  - 钩子：无（同父级理由）。

  **`parse`（第2层）**
  - 本质：在"双向映射纯函数集合"约束下，本子模块是**逆向映射器**（自然语言 → 结构），
    且是**全模块唯一持有时间状态的地方**（跨 chunk 的解析状态机）。
  - 四层：规范=定界符与状态枚举；存储=实例内的 `buffer` 与 `state`（生成级私有）；流转=状态机跳转；接口=`feed` / `extract`。
  - 钩子：无。但需显式保证**异常路径也清空 buffer**（`finally`），否则流式中断会残留生成级状态。

## 验证方式

### 前置条件 P（空间是否就绪）

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| P1 | 依赖 | `pip install -r requirements.txt` 可完成（含 `wasmtime`） |
| P2 | Token | `.env` 中至少 1 个可用平台（DeepSeek/Kimi/豆包/智谱/MiniMax） |
| P3 | **基线快照** | 改造**前**录制「不传 `tools`」的响应快照，作为 I1 比对基准 |
| P4 | 服务 | `python main.py` 可起，`GET /v1/models` 返回 61 个模型 |

### 后置条件 Q（时间流是否正确）

| 编号 | 检查项 | 通过标准 |
|---|---|---|
| Q1 | 工具识别 | 传入 `tools` 后返回的 `tool_calls[].function.name` 属于已声明工具集 |
| Q2 | 多轮闭环 | 回传 `role:"tool"` 结果后，模型产出基于该结果的最终答案 |
| Q3 | 流式一致 | 同一 prompt 下，流式聚合结果与非流式结果在"工具名 + 参数"上等价 |
| Q4 | 参数合法 | `arguments` 可被 `json.loads` 解析（R2） |

### 不变量 I（规则是否全程守住）

| 编号 | 不变量 | 判定方式 |
|---|---|---|
| **I1** | 不传 `tools` 时响应**逐字段等价**改造前 | 与 P3 快照做 diff，必须为 0 |
| I2 | 解析失败降级为 `content`，不得 5xx | 注入畸形输出用例，断言 HTTP 200 |
| I3 | `/v1/models` 与 7 个 provider 的既有 chat 路径零改动 | `git diff` 范围审查 + 旧路径回归 |
| I4 | 无新增运行时依赖 | `requirements.txt` 无 diff |
| I5 | 无状态泄漏 | 同进程连续 100 次混合请求（带/不带 `tools`），末次行为与首次一致 |

### L 维度（协同产品必需）

工具调用是**模型行为**，必须用 LLM 维度量化。固定用例集 × ≥80% 成功率门槛：

| 用例 | 期望行为 |
|---|---|
| U1 单工具 + 中文明确触发 | 返回 1 个正确 `tool_call` |
| U2 多工具需选择 | 选对工具，参数合法 |
| U3 诱导（无需工具即可回答） | **不**返回 `tool_calls`，直接作答 |
| U4 需并行调用两个工具 | 返回 2 个 `tool_calls`（P4 目标；未达成时记录为已知限制） |
| U5 工具结果回传后继续 | 产出基于结果的最终答案 |

统计口径：`成功率 = 符合期望的用例数 / 总用例数 × 分平台样本数`；
**某平台 < 80% 时，在 README 标注"不建议用于 agent"**。

### 判定逻辑（§5.2）

| P | Q | I | L | 决策 |
|---|---|---|---|---|
| ❌ | - | - | - | 阻断，修复前置 |
| ✅ | ✅ | ✅ | ✅ | 保留（commit） |
| ✅ | ✅ | ❌ | ✅ | 回退（规则被破坏） |
| ✅ | ❌ | ✅ | ✅ | 回退（时间流执行错误） |
| ✅ | ✅ | ✅ | ❌ | 回退（L 维度失败，成功率不达标） |

## 项目愿景

**演进路径**：

1. **本期**：提示词模拟工具调用（方案 A），覆盖 OpenAI 兼容客户端，5 个可用平台。
2. **下一期（可选）**：新增 `official` 直通 provider —— DeepSeek / 通义 / 智谱 / Moonshot / MiniMax
   官方端点原生支持 `tools`，可绕过 Web 逆向的脆弱性（顺带把千问从"被 WAF 拦住"变成可用）。
3. **再下一期（可选）**：Anthropic `/v1/messages` 端点，支持 Claude Code / CodeBuddy 类客户端。
4. **远期**：按平台维护"工具调用成功率"指标，低成功率平台自动降级为纯聊天并在 `/v1/models` 标注能力。

**设计遗产**：本层把「无工具能力的上游」抽象成可插拔的翻译策略（渲染 + 解析），
未来若某平台上支持原生 tools，只需为其增加一条**直通策略**，无需改动编排层与接口层。
