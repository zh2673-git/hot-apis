## 1. 静态依赖视图（谁可以依赖谁）

```
┌──────────────────────────────────────────────────────────────────────┐
│ interfaces   src/api.py                                              │
│              /v1/chat/completions   /v1/models                       │
│              依赖 ↓ 允许                                               │
├──────────────────────────────────────────────────────────────────────┤
│ application  src/tools/pipeline.py                                    │
│              依赖 ↓ 允许                                               │
├───────────────────────────────────────┬──────────────────────────────┤
│ domain       src/tools/render.py      │ src/tools/parse.py           │
│              src/tools/spec.py        │                              │
│              依赖 ↓ 允许（仅此处出口）  │                              │
├───────────────────────────────────────┴──────────────────────────────┤
│ core         src/models/schemas.py     ← 零依赖，规则基座              │
└──────────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────────┐
│ infrastructure  src/providers/*.py（7 个，本次不改）                   │
│                 仅被 pipeline 通过**参数注入**使用，不反向依赖 tools     │
└──────────────────────────────────────────────────────────────────────┘
```

**依赖铁律**：

| 铁律 | 本项目落实 | 违反后果 |
|---|---|---|
| 空间防越界 | `src/tools/*` **不得 import 任何 provider**；provider 实例由 `api.py` 通过参数传入 `pipeline` | 领域逻辑绑定具体上游 → 新增平台要改翻译层 |
| 时间防乱序 | `tools` 层不触碰 `providers` 的 `_sessions`、不发起上游调用；只做纯计算 | 翻译层与调度耦合 → 无法独立测试 |
| 规则防穿透 | 跨层数据一律是 `schemas.py` 的类型，禁止裸 dict 在层间流转 | 契约失效，字段漂移无人拦截 |

> 校验方式：`grep -rn "providers" src/tools/` 必须为空（除注释）。

  │                      │        │        render_messages     │                │
  │                      │        │◄── 单条 user 文本 ──────────┤                │
  │                      │        ├─ chat_completion_stream ───────────────────►│
  │                      │        │◄──────── 上游自然语言 token 流 ─────────────┤
  │                      │        ├───────────────────────────►│ feed(chunk)    │
  │                      │        │◄── Event: CONTENT / TOOL_CALL ──────────────┤
  │◄── SSE chunk ────────┤◄───────┤                            │                │
  │    (content /        │        │                            │                │
  │     tool_calls delta)│        │                            │                │
  │                      │        │ 生成结束 → finish()        │                │

**时间形态**：主干是**顺序管道**；`parse.feed()` 内部维持

## 3. 技术选型理由（必须说明如何满足时空需求）

| 选型 | 空间需求（数据归属） | 时间需求（执行流） | 规则需求（约束拦截） |
|---|---|---|---|
| **不引入新依赖**（标准库 `json` + 手写状态机） | 不新增常驻内存结构（如 jsonschema 的编译缓存） | 不新增线程/协程 | 解析规则自持，不受第三方版本漂移影响 |
| **提示词模拟（方案 A）** | 工具语义只存在于"请求作用域文本"中，不进常驻空间 | 与既有上游调用同一条时间线，不新增并发 | 失败可降级为纯文本，规则层可控 |
| **无状态设计（不驻留多轮状态）** | ✅ 消灭跨请求共享空间 | ✅ 消除"会话缓存过期 → 上下文错乱"的时间耦合 | 正确性由客户端携带的历史保证（OpenAI 语义） |
| **历史压平成单条文本** | 压平动作在请求作用域完成，中间产物随请求回收 | 无额外时间开销（一次字符串拼装） | 规避上游"只取最后一条 user"的隐式截断规则 |
| **流式状态机解析** | `buffer` 为生成级私有，`finally` 清空 | ✅ 支持跨 chunk 边界（无法整包解析） | 必须假设模型输出不可信 → 多格式 + 降级 |
| **`api.py` 前置分支（`if not tools: 原逻辑`）** | 原路径不接触任何新对象 | 原路径时间线完全不变 | ✅ 这是 I1「逐字段等价」的结构性保证 |
| **不新增配置项** | 无新配置空间 | 无需启动顺序调整 | 规则硬编码在 `spec.py`，无配置漂移 |
| **不引入 Anthropic `/v1/messages`** | — | — | 范围收敛，避免规则双写 |

## 4. 关键设计决策记录（ADR）

### ADR-1：为什么用提示词模拟而不是等上游支持

- **背景**：7 个上游全是 Web 逆向的聊天接口，无 `tools` 参数。
- **备选**：① 等/推动上游支持（不可控）；② 改用官方 API 直通（需 Key、计费，属 B 方案）；
  ③ 本地模型代解析（无法凭空产生工具语义）。
- **决策**：③ 不成立，① 不可控 → 选 ②' 的**前置替代**：在 relay 内做提示词模拟。
- **后果**：工具调用质量依赖模型遵循度 → 必须用 L 维度量化（≥80%）。

### ADR-2：为什么工具调用多轮状态不驻留 relay

- **背景**：agent 每轮携带完整历史；relay 已有 `provider._sessions` 缓存。
- **备选**：① 服务端维护会话（按 session id）；② 客户端全量携带（无状态）。
- **决策**：②。理由：① 会引入跨请求空间与过期时间线（现状 `qwen` 用整段消息哈希做 key，
  agent 场景每轮必变 → 每轮新建会话 → 上下文全丢，已实测确认）。
- **后果**：每轮 prompt 变长（历史全量渲染）→ 需在 `render` 层控制体积（见 P2 研究方向）。

### ADR-3：流式解析取"缓冲判定（策略甲）"

- **备选**：甲=先判定再输出（首字稍慢，输出干净）；乙=边流边发、尾部补 `tool_calls`（首字快，但客户端可能同时收到引导语与工具调用而误判）。
- **决策**：甲，并叠加**快路径嗅探**：首个非空白字符不是 `<` / 反引号时立即切直通模式，正常文本零额外延迟。
- **后果**：工具调用场景首字延迟 = 到 `</tool_call>` 出现为止（可接受，工具调用本就要等完整 JSON）。

### ADR-4：多格式容错而非单一严格格式

- **备选**：① 只认 `<tool_call>`；② 同时认标签 / ```json 围栏 / 裸 JSON。
- **决策**：②。理由：时空规则决定"输出不可信"，单一格式在中文模型上成功率不足。
- **后果**：解析器复杂度上升 → 必须有单元级测试与畸形输入用例（Q4/I2）。

### ADR-5：历史压平 vs 多消息透传

- **背景**：`kimi`/`doubao`/`qwen` 只发最后一条 user 消息，`deepseek` 拼纯文本，`zhipu` 拼 `<|system|>` 风格。
- **备选**：① 改这 5 个 provider 支持多消息（违反 R5，回归面大）；② 在 `render` 层压平（provider 无感）。
- **决策**：②。压平后所有 provider 都收到「一条包含完整上下文与工具规范的 user 文本」。
- **后果**：`deepseek` 会额外包一层 `[System]:` 标注，属可接受的冗余（不改变语义）。

### ADR-6：本次不含 Anthropic 端点

- **理由**：范围锁定 OpenAI 兼容客户端；`/v1/messages` 需另一套请求/响应/流式事件（`content_block_delta` 等）与工具语义，属独立迭代。
- **后果**：Claude Code / CodeBuddy 类客户端暂不可用，`program.md` 已显式记录。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型不遵守工具调用格式 | 工具调用失败 | 多格式容错（ADR-4）+ 降级为文本（R2）+ L 维度量化门槛 80% |
| 模型"先写引导语再调工具" | 客户端可能误判 | 策略甲缓冲判定 + 提示词明确"只输出 tool_call，不要其他文字" |
| 历史压平后 prompt 过长 | 上游截断 / 成本上升 | P2 研究方向：历史渲染策略与体积控制 |
| `tool_calls` 的 id 非模型产出，是 relay 生成 | 多轮 `tool_call_id` 对应关系必须自洽 | id 由 relay 生成并回传时**原文照抄**到 `role:"tool"` 的匹配校验（R4） |
| 上游协议变更（近两天已三变） | 工具层连带失效 | 工具层只依赖"上游能返回自然语言"这一最弱假设；协议细节封装在既有 provider 内 |
| `content` 放宽为可选引入语义缝隙 | 不传 `tools` 且 `content=null` 的请求可能异常 | 在非 tools 路径显式校验并返回 400（见 `03-模块设计.md` §2.1） |
| 千问 / 秘塔上游不可用 | 可验证平台仅 5 个 | 方案外约束；README 已标注；验证报告如实记录跳过项 |
